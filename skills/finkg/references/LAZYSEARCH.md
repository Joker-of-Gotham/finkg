# LazySearch：怎么问、怎么落盘、怎么把信息用尽

服务地址来自使用者的工作区配置（`fg doctor` 能看到是否已配置），skill 本身不携带任何地址。

## 为什么必须落盘

一次真实测量：问「宁德时代2025年营业收入和净利润」

| 层 | 字符数 | 内容 |
| --- | --- | --- |
| `final_answer` | 474 | 已综合好的结论，几个关键数 |
| `history` 里的 tool 返回 | 11,814 | 证券实体候选表、利润表 **83 列**原始 CSV、成长能力指标表、执行过的 SQL、源库表名 |

**结论只占返回信息量的 4%。** 只看结论就等于把 96% 的检索成果扔了——而且扔掉的恰恰是能让公司节点属性变丰富的那部分。

落盘还解决两个问题：

- **可追溯**：事实的 `quote` 必须能在落盘原文里找到，工具会核验。没落盘就没法核验，事实也就无法回溯。
- **渐进式披露**：几万字符不必进上下文。落盘后按需分层取用，要哪张表取哪张表。

## 两条通道

```bash
fg search "<问题>"                                  # HTTP /api/query，拿全 history，首选
fg search "<问题>" --channel mcp                    # 走 MCP，只有结论
fg harvest add "<问题>" --file reply.txt --channel mcp   # 你自己调 MCP 之后补落盘
```

宿主里直接调 MCP 工具（端点是配置里的地址加 `/mcp`，注意末尾无斜杠）在对话里交互很方便，但它只回结论。**用了 MCP 就必须 `harvest add` 补落盘**，否则这次检索不进核账、不可回溯。

两者不矛盾：探路时用 MCP 快速试水，确认方向后用 `fg search` 正式取数。

## 分层取用一次收割

```bash
fg harvest show h-0001 --part summary                  # 规模、用了哪些内部工具、源表
fg harvest show h-0001 --part provenance               # 源库表 + 执行过的完整 SQL
fg harvest show h-0001 --part answer                   # 结论
fg harvest show h-0001 --part data                     # 全部原始工具返回
fg harvest show h-0001 --part data --block 5            # 只要第 5 个返回
fg harvest show h-0001 --part data --grep "毛利|存货"   # 只要匹配行
fg harvest show h-0001 --part cells                    # 逐单元格清单
fg harvest show h-0001 --part cells --unused-only       # 还没落进图的单元格
fg harvest show h-0001 --part cells --grep "研发"        # 定位某科目
```

`--part provenance` 的价值常被低估：LazySearch 执行的 SQL 里带**全部字段的中文别名**。一次利润表查询的 SQL 就列出了 82 个中文科目名（营业总收入、营业税金及附加、对联营企业和合营企业的投资收益、以摊余成本计量的金融资产终止确认收益……）。这是节点属性该有哪些字段的现成清单。

## 十个检索扇区

广度收割按扇区铺开，每个扇区至少一次检索。缺哪个扇区，图就在哪个方向上没有纵深。

| 扇区 | 要拿到什么 | 怎么问 |
| --- | --- | --- |
| **1 身份与证券** | 法定名、代码、ISIN、交易所、资产类别、股本、市值、上市地 | 「解析 X 的证券实体，A股/港股/美股候选都列出并说明区别」 |
| **2 财务报表** | 三大报表逐科目、多个报告期 | 「X 2023/2024/2025 年合并利润表全部科目与数值，不要摘要」 |
| **3 财务指标** | 成长、盈利、偿债、营运、每股 | 「X 最近 3 个报告期财务指标（成长能力）与（盈利能力）全部字段」 |
| **4 业务构成** | 分部/产品/地区收入、成本、毛利率、占比、同比 | 「X 最新主营业务构成及对应营收、成本、毛利率、占比、同比增长率」 |
| **5 所有权与治理** | 十大股东、持股比例与性质、实控人、董监高 | 「X 最新报告期前十大股东、持股数量、持股比例、股东性质」 |
| **6 供应与产能** | 客户、供应商、产能、利用率、在建、长协 | 「X 主要客户与供应商、产能与产能利用率、在建工程」 |
| **7 行情与估值** | OHLCV、市值、PE/PB/PS、波动、成交、换手 | 「X 最近 60 个交易日日线与市值、PE(TTM)、PB」 |
| **8 上游要素** | 原料价格、产量、开工率、库存、进出口 | 「碳酸锂 2024-2026 月度价格、产量、开工率、库存」 |
| **9 政策与事件** | 监管规则、准入、补贴、处罚、诉讼、重组 | 「X 所属行业最近的监管政策变化与 X 的公告、处罚、诉讼」 |
| **10 预期与风险** | 分析师预期、一致预期、指引、风险因子 | 「X 的分析师盈利预测与一致预期 EPS；年报披露的主要风险因素」 |

十个扇区里，**5、6、8、9 是产生边最多的扇区**，也是最容易被跳过的。跳过它们，图就只剩一堆孤立的财务节点。

## 提问法

### 让返回变丰富的四条

1. **一次一个可判定事项，但要求穷尽。** 「全部科目」「全部行」「全部字段」「不要摘要」「列出所有」。
   - 好：「宁德时代 2025 年合并利润表全部科目与数值，不要摘要」→ 83 列
   - 差：「宁德时代 2025 年业绩怎么样」→ 几句话
2. **把口径写进问题。** 币种、单位、报告期还是时点、合并还是母公司、是否复权、数据状态（是否已调整）、频率。口径没说清，取回来的数就没法用，事实校验也会因缺单位/期间而失败。
3. **有歧义就要求列全候选。** 「如果有多个同名实体，全部列出并说明区别」。同名公司、A/H 双重上市、母子公司同名都很常见。
4. **要求给出源表名与执行的 SQL。** 「并给出你查询的源表和执行的 SQL」。这既是回溯依据，也让你知道下次可以直接点名那张表。

### 点名工具与库表（先建环境档案）

在查询里直接说工具名或库表名，LazySearch 会照着走。这是把「模糊检索」变成「精确取数」的
关键，也是让一次返回从几百字符变成几万字符的关键。

但**每套部署能查到的表和可用的工具都不一样**，所以 finkg 不内置任何表名清单——
那属于你机构的内部信息，也会随部署漂移。清单记在你自己的环境档案里：

```bash
fg env             # 读你这套环境已知的表与工具
fg env --init      # 第一次用，先建一个空档案
```

**第一次用先做一轮探索，把档案填起来。** 一次性投入十几分钟，之后长期复用：

```
列出你可以调用的全部检索工具，说明每个工具适合什么问题、需要哪些参数
探索一下有哪些和「公司财务报表」相关的数据表，给出库名、表名和字段 schema
探索一下有哪些和「股东持股」相关的数据表，给出库名、表名和字段 schema
探索一下有哪些和「主营业务构成 / 分部数据」「行情与估值」相关的数据表
```

档案填起来之后，查询就能这样写（把尖括号换成你档案里的真实名字）：

```
先用 <表探索工具> 探一下 <库名> 里与股东持股相关的表并给出 schema
用 SQL 从 <库.持股表> 关联 <库.证券代码映射表>，取 <代码> 最新报告期前十大股东的
姓名、持股数量、持股比例、股东性质，并给出执行的 SQL
```

**每次取数后顺手补档案。** `fg harvest show <id> --part provenance` 会给出这次实际调用过的
工具名、源库表和完整 SQL —— SQL 里通常带着全部字段的中文别名，那就是现成的字段清单。
抄进 `finkg.environment.md`，下次直接点名。

### 追问链

单次检索很难拿全。标准链路是四步，每步都落盘：

```
① 实体解析   → 拿到准确代码与候选区分
② 表探索     → 知道哪张表有你要的字段
③ 精确取数   → 点名表与字段，要求全部行
④ 交叉核对   → 换一个来源或口径验证同一个数
```

第 ④ 步是纵深图的必需品，不是可选项：只有一个来源支撑的关键数字，在质量报告里会体现为「一根链，没有交叉验证」。

## 收割纪律

**落盘 ≠ 用过。** 每次收割在索引里有状态：`unmined` → `partial` → `mined`。

```bash
fg harvest list --state unmined     # 还没挖的
fg harvest mine h-0001 --done    # 读取会话 drafts/ 下的实体与事实草稿
```

挖掘的粒度是**逐表、逐行、逐单元格**：

1. `--part cells` 列出这次收割的全部数据单元格（表格单元格 + 正文里的数值）。
2. 每个单元格要么变成一条事实（节点属性 / 边 / 边属性），要么写明为什么不用。
3. 不用的写处置理由：

```bash
fg harvest dispose h-0001 --scope "数据状态" --reason "库内版本标记，不是业务事实"
fg harvest dispose h-0001 --scope "内部更新时间" --reason "ETL 时间戳，与业务无关"
fg harvest dispose h-0001 --scope "已赚保费" --reason "保险业专用科目，本公司为 0/空"
```

`--scope` 是列名或上下文片段的子串，`*` 表示整次收割。

## 信息利用率核账

```bash
fg usage
```

输出三个比率，逐次收割给出：

| 指标 | 含义 |
| --- | --- |
| `use_ratio` | 数据单元格中真正进了图的比例 |
| `accounted_ratio` | 进了图 **或** 写明了不用理由的比例 |
| `open` | 既没用也没交代的单元格数，以及具体样本 |

`open_samples` 会直接给出还没用的科目和它所在的行，例如「营业总成本 3,448.24 亿 / 344,824,196,000.00」。看到这种就说明利润表只挖了一半。

判定规则：一个单元格算「已用」的条件是它的取值出现在某条事实的 `quote`、`object.value` 或边属性里。**所以引文摘整行比摘单个数字划算**——摘「研发费用 | 221.47 | 22,146,581,000.00」一次覆盖三个单元格，也更利于回溯。

目标值随质量档不同（`probe` 50% / `standard` 75% / `deep` 85%），但方向只有一个：**要么用，要么说清为什么不用，不许静默丢弃**。

## 一次典型的收割到事实

```bash
fg search "宁德时代2025年年报合并利润表全部科目与数值，不要摘要" --tag 财务
# → h-0001，684 个数据单元格

fg harvest show h-0001 --part provenance          # 拿到 82 个中文科目名
fg harvest show h-0001 --part data --grep "营业|利润|费用"
# 逐行写成事实，quote 摘整行
fg harvest mine h-0001 --done
fg usage                                          # 看这次挖到了多少
```

一次利润表收割应该产出**几十条**节点属性事实（每个非空科目一条），不是三五条。公司节点的财务维度就是这样堆起来的。
