# 节点属性：让每个节点自己就是一份详表

## 属性命名法

属性名用**点分中文层级**，第一段是维度组：

```
财务.利润表.2025年报.营业总收入
财务.每股指标.2025年报.基本每股收益
身份.统一社会信用代码
所有权.第一大股东.持股比例
行情.2026-08-12.收盘价
风险.供应链.关键原料集中度
```

这样做有三个直接好处：

- **维度组自动统计**：质量报告按第一段分组，一眼看出「这家公司只有财务，没有所有权和风险」。
- **同一指标多期共存**：`财务.利润表.2024年报.营业总收入` 与 `…2025年报…` 是两个属性，不会互相覆盖。
- **Neo4j 里可直接查**：属性通过参数化 map 写入，中文和点号都不需要转义。

不要用英文键、不要用下划线拼音、不要把多个值塞进一个属性。

## 每个属性带的元数据

值本身写在 `object` 里，口径写在事实上，编译时自动附到属性：

```json
{
  "subject": "E-catl", "predicate": "营业总收入",
  "object": {"kind": "number", "value": 423701834000.0, "unit": "元", "currency": "CNY"},
  "period": {"kind": "duration", "start": "2025-01-01", "end": "2025-12-31", "label": "2025年报"},
  "basis": {"consolidation": "合并报表", "standard": "中国会计准则",
            "source_table": "<取数用的库.表>", "data_status": "已调整最终版"},
  "epistemic": "reported", "known_at": "2026-03-10", "confidence": "high",
  "harvest_id": "h-0001",
  "quote": "归属于母公司股东的净利润 | 722.01 | 72,201,282,000.00",
  "target": {"kind": "prop", "node": "E-catl", "key": "财务.利润表.2025年报.营业总收入"}
}
```

- 数值必须有 `unit` 或 `currency` 或 `percent`，且必须有 `period`。缺了就是不可用的数，质量报告会判 error。
- `epistemic`：`reported`（披露）/ `observed`（市场观测）/ `estimate` / `forecast` / `inference` / `scenario` / `disputed`。后四类必须写 `basis_fact_ids` 和 `rule`。
- 裸 `$` 不推定美元，裸「元」不推定人民币——`currency` 要有明确来源语境。
- `fg node <id>` 会把这些一并显示出来，包括原文引文。

## 不要造空属性

丰富指的是**已知且有证据的字段数**，不是字段目录长度。

- 没查到就不要写这个属性。空字符串、`"未知"`、`"N/A"` 都会让节点看起来完整而实际是空的。
- 确实查过但对方未披露，值得记一笔时用文本属性写清：`披露状态.客户集中度 = "年报未按客户披露"`，并照常带 `quote` 与 `harvest_id`。
- 只有名字没有属性的业务节点会在 `fg quality` 里被点名（`name_only_nodes`）。要么补，要么删。

## Company：八个维度组

字段名直接沿用 LazySearch 返回里的中文名，能对得上原文最省事。

| 组 | 字段（按可得性挑，不必求全） |
| --- | --- |
| **身份** | 法定名称、英文名称、常用简称、统一社会信用代码、LEI、CIK、注册地、注册资本、成立日期、法定代表人、企业性质、证券代码 |
| **报告** | 会计年度、记账币种、会计准则、审计机构、最新年报公告日、首次公告日、报表合并类型、数据状态 |
| **行业** | 证监会行业、申万行业、GICS、主营范围、所属产业链环节、主要市场区域 |
| **业务** | 主营业务项目及收入/成本/毛利率/占比/同比、主要产品、产能、产能利用率、在建产能、主要客户、客户集中度、主要供应商、供应商集中度、员工人数、研发人员占比、专利数 |
| **财务** | 利润表逐科目（营业总收入、营业收入、营业总成本、营业成本、营业税金及附加、销售/管理/财务/研发费用、利息收入与支出、投资收益、对联营合营企业投资收益、公允价值变动收益、资产与信用减值损失、营业利润、利润总额、所得税费用、净利润、归母净利润、少数股东损益、综合收益总额、基本/稀释每股收益）；资产负债表逐科目；现金流量表逐科目；成长/盈利/偿债/营运能力指标 |
| **资本** | 总股本、流通股本、股本结构、有息负债、资产负债率、货币资金、评级、授信额度、债券余额、分红与回购 |
| **所有权** | 控股股东、实际控制人、前十大股东及持股数量/比例/性质、重要子公司及持股比例、联营合营企业 |
| **治理** | 董事长、总经理、财务负责人、董事会构成、高管薪酬、股权激励 |
| **风险** | 监管处罚、重大诉讼、担保与质押、关键原料集中度、客户集中度风险、汇率与利率敞口、ESG 事项、年报披露的主要风险因素 |

**一个锚点公司应该有几十个属性，横跨 6 个以上维度组。** 一次利润表检索就能贡献 40+ 个财务属性；不到这个量级说明收割没挖尽（见 `LAZYSEARCH.md` 的信息利用率）。

## Stock：八个维度组

公司和股票必须是两个节点，用「发行」「上市」类关系连起来。公司报财务，股票有行情与估值——混成一个节点会让口径全乱。

| 组 | 字段 |
| --- | --- |
| **证券身份** | 证券简称、交易代码、ISIN、FIGI、CUSIP、SEDOL、股份类别、资产类别、发行人 |
| **股本** | 已发行股数、流通股数、自由流通股数、限售股数 |
| **上市** | 交易所、MIC、板块、上市日期、交易币种、交易状态、涨跌幅限制、投资者适当性 |
| **行情** | 日期、开/高/低/收、成交量、成交额、换手率、VWAP、总市值、流通市值、区间涨跌幅、波动率、Beta |
| **估值** | PE(TTM)、PE(静)、PB、PS、EV/EBITDA、股息率、市值/自由现金流 |
| **流动性** | 日均成交额、买卖价差、融资余额、融券余额、转融通 |
| **持有人与指数** | 机构持股比例、北向持股、基金重仓、所属指数、指数权重 |
| **公司行动** | 分红派息、送转、增发、回购、拆并股、停复牌 |

**每个行情属性必须带观测时点与复权口径**：`行情.2026-08-12.收盘价` + `basis: {"adjustment": "未复权", "provider": "QuantWeb"}`。不同复权口径的价格不能混在同一个属性名下。

## 其他节点类型

| 类型 | 关键维度组 |
| --- | --- |
| `Listing` | 上市（交易所、板块、币种、生效期间）、交易规则、状态变更 |
| `Segment` | 业务（项目类别、主营业务收入/成本/利润、占比、毛利率、同比）、期间 |
| `Product` | 规格与性能、产能、价格、成本结构、认证、下游应用 |
| `Facility` | 位置、设计产能、投产时间、利用率、投资额、能耗与许可 |
| `Commodity` | 品种规格、价格时序、产量、开工率、库存、进出口、成本曲线 |
| `Person` | 任职、任期、持股、薪酬、关联关系 |
| `Institution` | 机构类型、管理规模、持仓、监管身份 |
| `Policy` / `Regulator` | 发布机构、生效时间、适用范围、约束内容、处罚条款、过渡期 |
| `Event` | 事件类型、宣布/发生/生效/终止时间、金额、条件、进展状态、影响主体 |
| `Risk` | 风险类别、暴露主体、风险因子、传导路径、触发条件、领先指标、可能性、影响量级、缓释措施、失效条件 |
| `Expectation` | 预期主体（公司指引/分析师/一致预期/市场隐含/情景）、预测指标、预测期间、数值、发布时间、发布方 |
| `Industry` | 分类体系与代码、市场规模、增速、集中度、产业链位置 |
| `Index` | 编制方、成分数、权重规则、调样周期 |

`Risk` 与 `Expectation` 是最容易被忽略却对纵深最关键的两类——它们分别撑起「风险与二阶反馈」和「预期与估值」两个语义层（见 `DEPTH.md`）。

## 实体记录

节点的身份信息写在实体记录里，属性写在事实里：

```json
{
  "id": "E-catl", "kind": "Company",
  "name": "宁德时代新能源科技股份有限公司", "short": "宁德时代",
  "aliases": ["CATL", "Contemporary Amperex Technology"],
  "ids": {"证券代码": "300750.SZ", "统一社会信用代码": "…"},
  "anchor": true,
  "note": "与「宁德时代新能源科技有限公司」（子公司）区分"
}
```

- `id` 用稳定可读的 slug（`E-catl`、`E-catl-a`、`E-ganfeng`），不要用序号。
- `short` 是 Neo4j 里显示的 caption，要短到能在图上看清。
- 有重名风险时 `note` 里写清区分依据——消歧不唯一时应该先问用户（见 `HITL.md`）。
- `kind` 用推荐词表里的值，纵深统计只把业务类型算作跳。`Document` / `Observation` / `Metric` 这类元类型不算跳，也基本不需要建：数值直接做节点属性就够了。

## 自查

跑 `fg node <id>` 看一个节点，问自己：

1. 拿这份详表给一个懂行的人看，他能不能不查别的东西就判断这家公司的经营与财务状况？
2. 每个数字的单位、币种、期间、合并口径是否都写了？
3. `fg quality` 里这个节点覆盖了几个维度组？缺的那几组是没查还是查不到？
4. 属性里有没有互相矛盾的两个值（`prop_conflicts`）？矛盾就交给用户判，不要静默取一个。
