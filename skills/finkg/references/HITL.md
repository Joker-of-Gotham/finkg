# 人在回路：对齐点，不是审批点

## 这里没有什么

没有 Gate、没有阶段门、没有签名、没有 HMAC、没有一次性令牌、没有工件哈希链、没有密钥环境变量。台账 `ledger.jsonl` 是明文 JSONL，随时可以打开看、可以手改、可以删一行重写。

它记录的是**「我们商量过什么、你怎么决定的、我据此改了什么」**，不是「谁被授权了」。质量报告同理：`ok=false` 只意味着「还不能对外声称达标、不该当成结论用」，它不批准也不阻止任何人类决定。

需要一个已知不达标的快照进 Neo4j 看看形状？`fg neo4j load --force`，然后继续干活。

## 唯一的机制：在对话里问，问完记账

用 **AskQuestion** 在对话里问用户。拿到答复后：

```bash
fg align --stage expansion \
  --question "宁德时代的海外产能该按基地建节点，还是并到区域分部？" \
  --option "按基地：德国图林根、匈牙利德布勒森各建 Facility 节点" \
  --option "按区域：欧洲产能并成一个 Segment 节点" \
  --recommendation "按基地。产能爬坡与政策约束是按基地发生的，合并会丢掉出口管制这条边" \
  --why-now "下一轮要补供给扇区，节点粒度定了才能设计检索"

fg answer "按基地建，但只保留已投产和在建的，规划中的不建" \
  --effect "新增 2 个 Facility 节点，规划产能改为写在公司节点的业务维度属性上"
```

`fg align` 只是留痕，它不会暂停你、不会返回特殊退出码、也不需要等什么东西解锁。`fg brief` 会把还没等到答复的对齐点列出来提醒你。

## 一个对齐点必须包含五件东西

只问「你同意吗」是无效的对齐——用户没有判断依据，只能说「可以」，而这不构成决定。

| 要素 | 为什么必须 |
| --- | --- |
| **当前判断** | 让用户知道你已经想到哪一步，而不是从零讨论 |
| **证据样本** | 摆出具体数字、原文引文、节点/边样本。抽象描述无法判断 |
| **2~3 个真实取舍** | 每个选项要写清它会改变哪些具体工件，以及代价 |
| **你的建议与理由** | 你比用户更清楚数据现状，先给判断再请他推翻 |
| **为什么现在必须定** | 说明再往下做会有多少工作建立在这个假设上 |

反面示例：「要不要扩大范围？」
正面示例：「现在锚点一跳邻居有 18 家公司，其中 6 家只能查到工商信息、查不到财务。三个选择：(A) 全留，图更全但会有 6 个只有名字的节点拉低可分析率；(B) 只留有财务的 12 家，图更实但会漏掉两家关键供应商；(C) 对这 6 家改用行业口径估算并标为 inference。我建议 B，因为断供风险那条链只需要那两家里的一家，可以单独补检索。选 A 的话我需要再跑约 10 次检索，大概会新增 200 个待挖单元格。」

## 六个自然对齐阶段

**不是流水线，是常见分歧点。** 有些会话在同一阶段来回好几次，有些阶段直接跳过。

| 阶段 `--stage` | 要跟用户定什么 |
| --- | --- |
| `scope` | 中心问题到底是哪一个；锚点是公司还是证券还是两者；时点与口径；用途（研究/尽调/监控）；质量档 |
| `sources` | 优先哪些数据源；关键数字要不要双来源；对预测与一致预期的采信程度；哪些扇区可以省 |
| `sample` | 先挖一次收割，把 20 条左右的事实样本摆给用户看：切分粒度、单位口径、属性命名、原子性对不对 |
| `expansion` | 节点粒度（基地 vs 区域、分部 vs 产品）；要不要收纳只有名字的外围实体；下一轮优先补哪个扇区 |
| `mechanism` | 哪几条链路必须能走通；`min_hops` 定多少；推断边的采信边界；替代解释怎么处理 |
| `delivery` | 装哪个 Neo4j 库；导出包含什么；残余局限怎么写清楚 |

`sample` 阶段最值得投入。**在挖第一次收割之后、大规模挖掘之前**把样本摆给用户看，能避免后面几百条事实按错误口径重做。

## 什么时候必须停下来问

- 同名实体、证券代码、上市地消歧不唯一；
- 两个来源对同一指标同一期间给出不同数值，或者合并/母公司、复权、重述口径无法确定；
- 出现多个高价值扩展方向，优先级取决于用户的真实用途；
- 一条关键边只能靠推断成立，且存在合理的替代解释；
- 已经对齐过的范围、锚点、机制问题需要推翻或回退（尤其是要删已有事实时）；
- 涉及付费来源、个人数据、对外写入、或任何交易/开户/授信/估值签字动作。

## 什么时候不该问

打扰太频繁和不打扰一样有害。这些不用问：

- 属性该叫 `财务.利润表.2025年报.营业总收入` 还是 `…营业收入`——按 `NODE_PROFILE.md` 的命名法定，不用问。
- 某个科目是不是要挖——挖，或者 `dispose` 写理由，不用问。
- 某条边的机制怎么写——回去检索，不用问。
- 质量报告里的每一条 finding——按 `QUALITY.md` 的顺序修，修不动的那一条才值得问。

判断标准：**这个决定依赖用户的业务意图或风险偏好吗？** 依赖就问，只依赖数据现状就自己定。

## 怎么把答复真正落地

答复不落到工件上等于没问。`fg answer --effect` 里写的应该是**具体改动**，不是「已知悉」：

```bash
# 好
fg answer "只保留有财务数据的 12 家" \
  --effect "删除 6 个 name-only 实体及其 9 条边，另对赣锋与天齐单独补检索"

# 无效
fg answer "好的" --effect "已记录"
```

落地之后重跑 `fg compile && fg quality`，确认改动确实反映在指标上。

## 台账长什么样

```bash
fg ledger --kind align --limit 20
```

```json
{"ts":"2026-08-13T11:02:15+08:00","kind":"align","stage":"expansion",
 "question":"海外产能按基地还是按区域？","options":["按基地…","按区域…"],
 "recommendation":"按基地","why_now":"节点粒度定了才能设计检索",
 "answer":"按基地建，但只保留已投产和在建的","answered_at":"2026-08-13T11:05:40+08:00",
 "effect":"新增 2 个 Facility 节点，规划产能改为公司节点属性","actor":"user"}
```

台账同时记录 `harvest`、`harvest_mined`、`facts_added`、`compiled`、`neo4j_loaded` 等动作，所以它也是这次会话的完整工作日志。导出包里会带上它——交付时对方能看到每个判断是怎么来的。

## 跨宿主

这套机制不依赖任何宿主的特殊能力：没有 AskQuestion 工具时，就在回复里把五件要素写清楚然后停下来等；用户回复后照样 `fg align` + `fg answer` 记账。不要因为没有原生交互组件就替用户做决定。
